## 1. 标记说明

### 优先级

| 标记 | 含义 |
|---|---|
| P0 | 第一版必须有，决定规范库是否成立 |
| P1 | 高价值，依赖少，紧随第一版 |
| P2 | 需要前置数据、账号、网络控制或页面改造 |
| P3 | 后续增强 |

### 实现阶段

| 阶段 | 范围 |
|---|---|
| S1 | 表单规范 v1：必填、长度、格式、正常流 |
| S2 | 重复校验、错误文案发现、AI 语义识别、覆盖统计 |
| S3 | 项目规则、列表、CRUD、权限、状态流转 |
| 后续 | 上传、网络异常、可访问性、数据驱动 |

### 依赖标记

| 标记 | 含义 |
|---|---|
| 静态 | 只看 HTML/标签即可生成，无副作用 |
| 探测 | 需要实际触发一次校验，读取错误文案 |
| 夹具 | 需要已有数据、账号、角色或文件 |
| 副作用 | 会创建/修改/删除数据，需要唯一数据或清理 |
| 项目配置 | 需要团队补充字段规则或预期文案 |

## 3. 第一版建议清单（S1）

建议第一版只勾选 P0 且不依赖夹具的规则：

- FORM-REQ-01 必填-空值
- FORM-REQ-02 必填-纯空格
- FORM-LEN-01 ~ FORM-LEN-04 长度四边界
- FORM-FMT-01 邮箱
- FORM-FMT-02 手机号
- FORM-FMT-03 数字
- FORM-SUBMIT-01 正常流

理由：

1. 全部可以从 HTML/标签静态识别，不需要账号、夹具或页面改造。
2. 覆盖「必填、长度、格式、正常流」四类最常见规范。
3. 每条都能生成明确断言，且不会产生难以清理的数据（正常流用唯一名称）。
4. 能在演示页上直接验收，适合做垂直切片。

S1 需要演示页补充：

- 内容名称：`required`、`maxlength=50`、`minlength=2`。
- 新增一个「邮箱」字段：`type=email`，便于验证格式规则。
- 保存成功后显示明确的成功提示，便于断言。

以上规则已随 S1 交付；`maxlength+1` 按浏览器截断处理（断言输入值被截为 max 且提交成功）。必填空值场景覆盖文本、数字、日期与没有默认值的下拉；纯空格是否视为空取决于产品 trim 规则，S1 不自动生成；已有默认值的下拉、无边界数字字段会明确跳过并给出原因。列表/查询页会自动打开「新建」表单后再分析。

## 6. 每条规则的实现约定

### 6.1 生成什么

一条规则可以生成多个场景。矩阵里一行一个场景，例如：

```text
FORM-LEN-01 长度-最小值-1
FORM-LEN-02 长度-最小值
FORM-LEN-03 长度-最大值
FORM-LEN-04 长度-最大值+1
```

### 6.2 预期从哪来

优先级：

1. HTML 约束（required/minlength/maxlength/pattern/type）。
2. 项目规则配置（字段 → 规则 → 参数/文案）。
3. 运行时探测（实际触发校验，读取错误文案）。
4. AI 建议（只作为候选，默认不勾选）。

### 6.3 断言怎么写

统一模板：

- 负向：`fieldInvalid` + `pageText contains`（错误文案）+ `urlContains`（未跳转）。
- 正向：`pageText contains`（成功提示）+ `urlContains` 或 `count + 1`。
- 重复：`pageText contains`（重复提示）+ `count`（数量不变）。
- 不确定：只断言「字段无效 + 未跳转」，不猜具体文案。

### 6.4 什么时候跳过

必须显式给出原因，并在矩阵里显示：

- 没有约束（长度/格式/范围）。
- 需要前置数据（重复、权限、列表）。
- 低置信度（AI 猜测）。
- 页面结构不支持（没有提交按钮、字段不可交互）。
- 操作有破坏性且未获确认。

### 6.5 副作用与清理

- 创建类：使用唯一名称（`规范测试_<时间戳>`），执行后提示可在列表中删除。
- 删除/批量：默认不勾选，必须用户确认。
- 重复校验：只使用已有值，不新建前置数据。
- 探测：优先失焦，其次提交后刷新；产生数据时记录并在报告中标注。

## 7. 评审问题

请重点确认：

1. **S1 范围**：必填/长度/格式/正常流是否够？要不要把「重复校验」提前？
2. **必填的判定**：只看 `required`，还是标签含「名称/手机号/邮箱」也默认必填？
3. **长度无约束时**：跳过，还是生成一个「超长 1000 字」的探索场景？
4. **格式规则**：手机号/邮箱/身份证等是否内置常见正则，还是要求项目配置？
5. **错误文案**：是否接受「运行时探测 + 用户确认」，还是必须项目配置？
6. **语义断言**：是否新增 `fieldInvalid` / `fieldError`？
7. **用例粒度**：一条场景一条用例，还是同一字段的多组数据合并成一条数据驱动用例？
8. **演示页改造**：是否同意补充 maxlength/email/成功提示，用于验收？
9. **权限与列表**：是否放到 S3，还是第一版就要一个最小列表规范？
10. **安全类输入**：特殊字符只做转义/保存验证，还是需要更完整的安全测试规范？
