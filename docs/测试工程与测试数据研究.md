# 测试工程与测试数据：开源方案研究与本地设计

> 目的：在动手做「测试套件 / 计划 / 批量执行 / 测试数据」之前，先看成熟项目怎么解，避免重复造轮子。
> 边界：本地优先、技术栈不变、不做服务端。研究结论只服务于本地功能设计。
> 版本：v1 · 2026-10-17

---

## 0. 结论先行

1. **测试管理模型不要自创**：直接借鉴 Kiwi TCMS 的 `Product → TestPlan → TestCase → TestRun → TestExecution`，并吸收「用例版本钉住执行」「执行状态按权重统计」「属性组合生成执行」三个设计。
2. **执行引擎不要重造**：Playwright Test 已经验证了 fixtures、setup/teardown、storageState、retries、trace、JUnit/GitHub reporter、sharding 这套组合；我们在本地按它的语义实现子集。
3. **测试数据要作为一等公民**：成熟做法是「环境配置 + 数据配方（fixtures/recipes）+ 生成器（factories）+ 数据集 + 唯一命名空间 + 清理」五件套，而不是在用例里硬编码。
4. **功能场景用测试设计技术驱动**：表单 → 等价类 + 边界值；查询 → 矩阵 + 边界；CRUD → CRUD 矩阵；流程 → 状态迁移；权限 → 权限矩阵。用例模板应内置这些结构。
5. **CI 只做 GitHub Actions**：本地 CLI 产出 JUnit XML，`mikepenz/action-junit-report` 在 PR 上做注释与检查；artifacts 存截图/Trace/报告。

## 2. Kiwi TCMS：测试工程模型（重点参考）

### 2.1 数据模型（代码级）

| 实体 | 关键字段/关系 | 对我们的意义 |
|---|---|---|
| Product / Version / Build | 产品、版本、构建 | 本地先简化为「项目 + 用例版本号 + 运行标识」 |
| TestPlan | product, version, type, tags, cases（通过 TestCasePlan + sortkey） | 计划绑定用例与顺序；可直接借用 |
| TestCase | summary, text（步骤/内容）, priority, category, status, author/default_tester/reviewer, requirement, is_automated, script, arguments, setup/testing duration | 用例不只是步骤，还有优先级、类型、前置、需求关联、自动化脚本 |
| TestCasePlan | plan, case, sortkey | 计划与用例多对多 + 排序 |
| TestRun | plan, build, manager, default_tester, planned/start/stop, tags, CC | 一次执行 = 计划 × 构建；记录执行人与时间 |
| TestExecution | run, case, assignee, tested_by, status, build, properties, case_text_version, start/stop, tags, defects | 每个用例（或每个数据组合）一条执行记录；**钉住用例版本** |
| TestExecutionStatus | name, weight, icon, color | 状态不写死；用 weight 计算完成/失败/通过率 |
| Environment / Property | 环境与属性；执行属性 | 环境 + 数据组合；支持笛卡尔积或 pairwise |

### 2.2 值得直接吸收的设计

1. **执行钉住用例版本**：`TestExecution.case_text_version` 指向当时的用例历史版本。执行后再改用例，历史报告不受影响。
2. **执行状态用权重而不是枚举**：通过/失败/阻塞/跳过都可以配置；统计只依赖 weight。本地可先用固定状态，但模型保留 weight。
3. **属性组合生成执行**：一个用例 + 环境/数据属性可以生成多条执行（笛卡尔积或 pairwise），这正好是数据驱动的底座。
4. **计划与用例多对多 + sortkey**：同一条用例可以进多个计划，顺序独立。
5. **需求字段**：`requirement` 先作为字符串，后续可扩展为需求实体，实现最轻量的可追溯性。

### 2.3 不照搬的部分

- 服务端、多用户、权限、邮件通知、MariaDB 树结构——本地不需要。
- 用例正文用纯文本/Markdown——我们继续用结构化步骤 JSON，但增加「前置条件 / 预期结果 / 备注」文本字段。

## 3. Playwright Test：执行模型（重点参考）

### 3.1 可借鉴机制

| 机制 | 做法 | 我们的本地落地 |
|---|---|---|
| Fixtures | 测试/Worker 作用域；setup 与 teardown 包在 `use` 前后 | 用例/计划的 setup、teardown 步骤；计划级共享登录态 |
| storageState | 登录一次，保存 cookies/localStorage，复用 | 本地「登录态」资产，绑定环境；计划执行前注入 |
| Retries | 失败重试，结果区分 passed / flaky / failed | 计划重试；run/attempt；flaky 标记 |
| Trace | `trace: on-first-retry`，失败可回放 | 失败用例默认开 Trace，本地保存并可在报告打开 |
| Reporters | list/html/json/junit/blob/github | 本地报告 + JUnit；GitHub Actions 用 JUnit action |
| Projects | 浏览器/角色/环境矩阵 | 计划的环境 × 设备 × 角色组合 |
| Sharding | `--shard` 分片 | 本地暂不做，L5 可选并行 |
| 测试独立 | 测试可单独运行、任意顺序 | 用例必须独立；数据用唯一命名空间 |

### 3.2 关键原则（来自 Cypress/Playwright）

1. **测试必须独立**，能单独运行、任意顺序运行。
2. **数据通过 API/程序化方式准备**，不要每个用例都走 UI 登录。
3. **清理放在测试之前**（Cypress 建议），避免上次失败残留影响下一次。
4. **不要用固定 sleep**，用元素/网络条件等待。
5. **用 data-* 选择器**，避免 CSS/文案耦合。
6. **每个并行 worker 用独立账号/数据**，避免共享状态。

## 4. 测试数据体系设计（核心）

### 4.1 成熟方案的五件套

| 层 | 成熟做法 | 我们的设计 |
|---|---|---|
| 环境配置 | env 文件 / profiles | 「环境」实体：baseUrl、账号、变量、浏览器/设备 |
| 数据配方（fixtures/recipes） | Playwright fixtures、Cypress `cy.task('db:seed')`、Robot setup | 「数据配方」：可复用的准备/清理步骤（API 或 UI） |
| 生成器（factories） | factory_boy、fishery、Faker | 内置生成器：唯一前缀、UUID、时间戳、随机字符串、邮箱、手机号、递增序号 |
| 数据集（datasets） | pytest parametrize、Robot 模板、CSV | CSV/JSON 数据集：列 → 变量；每行生成一次执行 |
| 隔离与清理 | 唯一 ID/命名空间、事务回滚、显式 teardown、Testcontainers | `RUN_ID` 命名空间 + 执行前清理 + 执行后清理 + 失败也清理 |

### 4.2 本地数据模型

```
Environment        环境：名称、baseUrl、配置变量、默认登录态
DataRecipe         数据配方：准备/清理步骤（HTTP/UI），可参数化
DataRecipeRun      配方执行记录（成功/失败/耗时）
Dataset            数据集：CSV/JSON，列定义、示例、校验
DatasetRow         数据集行（可存文件，也可存 DB）
DataProfile        数据档：环境 + 数据集 + 配方 + 变量覆盖
RunDataBinding     计划/执行与 DataProfile 的绑定
Secret             密钥：safeStorage 加密，只存密文
```

### 4.3 数据作用域与解析顺序

```
系统默认 < 项目 < 环境 < 数据档 < 计划 < 用例 < 数据集行
```

- `${var}`、`${secret.NAME}`、`${run.id}`、`${dataset.column}` 统一解析。
- 密钥只在实际执行时解密，报告/日志脱敏。
- `run.id` 由执行生成，用作唯一前缀（如 `atf-${run.id}-user@test.local`）。

### 4.4 生命周期

```
计划开始
  → 生成 run.id / 命名空间
  → 执行计划级 setup（登录、基础数据）
  → 对每个用例 / 数据集行：
      执行前清理（幂等）
      → 执行数据配方 setup
      → 执行用例步骤
      → 执行数据配方 teardown（失败也执行）
  → 执行计划级 teardown
  → 清理命名空间数据（API/UI；可选 DB）
```

### 4.5 隔离策略（按优先级）

1. **唯一命名空间**：所有创建的数据带 `run.id` 前缀/标记；适合 UI 与外部 API。
2. **执行前重置**：调用测试环境的 reset/seed API；适合有专用测试环境。
3. **显式清理**：按创建顺序反向删除；适合 API/文件/队列。
4. **事务回滚/独立 Schema**：需要数据库访问权限，作为后续可选能力。
5. **禁止**：共享固定账号/固定数据、生产数据、无清理、非幂等 seed。

### 4.6 数据设计规则

- 只创建用例需要的字段；其余走默认值/生成器。
- 唯一字段（邮箱、编号、名称）必须带 `run.id` 或序列，避免并行冲突。
- 时间相关断言使用相对时间（今天/未来）或固定时区。
- 敏感数据只用于测试环境；PII 用合成数据。
- 数据集要可评审、可复现；生成器要可设种子（同一 seed 复现同一批数据）。
- 清理顺序：子表 → 父表；外部资源先清理。

### 4.7 UI 设计

新增「测试数据」页（本地）：

- **环境**：列表、编辑、密钥掩码、测试连接。
- **数据配方**：步骤编辑（HTTP/UI）、参数、预览、测试运行。
- **数据集**：上传 CSV/JSON、列映射、示例预览、边界行模板。
- **数据档（Data Profile）**：环境 + 数据集 + 配方 + 变量覆盖。
- **引用关系**：哪些计划/用例使用了该数据档。
- **运行记录**：配方执行历史、失败原因。

## 5. 功能场景的测试设计模板

> 对应我们的高频场景：填表单、查询、CRUD、边界与异常。

### 5.1 表单校验矩阵

| 维度 | 取值 |
|---|---|
| 必填 | 空 / 仅空格 / 正常 |
| 长度 | min-1 / min / max / max+1 |
| 格式 | 合法 / 非法（邮箱、手机、日期、金额） |
| 字符 | 中文 / 英文 / emoji / 特殊字符 / 换行 |
| 重复 | 唯一字段重复 |
| 状态 | 禁用 / 只读 / 提交中 |
| 反馈 | 错误文案、字段高亮、提交按钮状态 |

### 5.2 查询矩阵

| 维度 | 取值 |
|---|---|
| 关键字 | 空 / 精确 / 模糊 / 无结果 / 特殊字符 |
| 组合条件 | 单条件 / 多条件 / 冲突条件 |
| 时间 | 今天 / 区间边界 / 跨时区 |
| 分页 | 首页 / 末页 / 越界页 / 每页条数 |
| 排序 | 升序 / 降序 / 多列 |
| 重置 | 清空条件后恢复默认 |

### 5.3 CRUD 矩阵

| 操作 | 正向 | 负向 |
|---|---|---|
| Create | 必填齐全、最小字段、最大字段 | 重复、非法格式、无权限 |
| Read | 列表、详情、搜索、分页 | 不存在、无权限、已删除 |
| Update | 单字段、全字段、并发编辑 | 非法值、版本冲突、无权限 |
| Delete | 单条、批量、软删除 | 不存在、有关联数据、无权限 |
| 持久化 | 刷新/重新登录后仍存在 | 删除后列表/详情不可见 |

### 5.4 状态迁移 / 权限矩阵

- 状态迁移：列出合法迁移与非法迁移，断言状态与按钮可用性。
- 权限矩阵：角色 × 操作 × 预期（可见/可编辑/可提交/拒绝），一条矩阵生成多行数据。

### 5.5 与平台的关系

- 这些模板不是硬编码，而是「用例模板 + 数据集列」：用户选择模板 → 生成数据集骨架 → 填值 → 批量执行。
- 每条数据集行 = 一次 TestExecution，报告按行分组，失败可定位到具体取值。
- 断言以「预期结果」列驱动：字段错误文案、列表条数、状态值、权限提示。

## 6. GitHub Actions 接入设计

### 6.1 目标

- 本地 CLI 在 CI 里跑计划；PR 上显示通过/失败与失败用例；artifacts 保留证据。

### 6.2 形态

```yaml
name: e2e
on: [pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: pnpm install --frozen-lockfile
      - run: pnpm -F @atp/runner exec playwright install --with-deps chromium
      - run: node packages/runner/dist/cli.js run --plan "$PLAN_ID" --junit junit.xml --headless
        env:
          ATP_DB: ${{ github.workspace }}/atp.db
          ATP_ENV: staging
      - uses: mikepenz/action-junit-report@v6
        if: success() || failure()
        with:
          report_paths: junit.xml
          comment: true
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: evidence
          path: artifacts/
```

### 6.3 需要的能力

- CLI 批量 `--plan`、`--junit`、`--headless`、`--env`。
- 证据目录约定：`artifacts/<runId>/...`。
- 退出码：0 通过 / 1 有失败 / 2 参数或环境错误。
- 数据库/计划随仓库分发：计划 JSON 包（可提交到仓库）或本地 SQLite（CI 上传/下载）。
- 测试环境依赖（DB/Redis）用 GitHub Actions service containers；被测系统自身由 CI 的部署步骤提供。

## 8. 对我们方案的修订

### 8.1 数据模型（本地）

在现有 `cases / case_steps / elements / runs / run_steps` 基础上增加：

- `case_versions`：用例快照（发布/执行钉住）。
- `suites / suite_items`：套件与排序。
- `plans / plan_items`：计划、用例、执行策略、环境。
- `plan_runs`（或 runs.plan_id）：计划执行。
- `executions`：用例 × 数据集行 × 环境；状态、耗时、证据、用例版本。
- `environments / variables / secrets`：环境与作用域。
- `data_recipes / datasets / dataset_rows / data_profiles`：测试数据体系。
- `execution_statuses`：状态与权重（可先用固定集合）。
- `requirements`（轻量）：需求编号/标题，用例关联。

### 8.2 里程碑调整

- **L1**：套件/计划/批量/重试/JUnit + **执行钉住用例版本** + iframe 修复。
- **L2（新增）**：测试设计模板与数据集骨架（表单/查询/CRUD/状态/权限）+ 新动作覆盖。
- **L3**：断言与证据（网络/控制台/软断言/Trace）。
- **L4**：测试数据体系（环境、配方、生成器、数据集、数据档、清理）+ setup/teardown + HTTP 动作。
- **L5**：度量、CI 完善、视觉/可访问性/性能、跨浏览器。

> 注意：测试数据的**模型**要在 L1 设计时预留，避免 L4 返工；但完整 UI 与执行可以放在 L4。

### 8.3 关键设计决策

1. **用例版本钉住执行**：每次执行保存用例快照（或版本号）；历史报告不随用例编辑变化。
2. **执行 = 用例 × 数据行 × 环境**：一条数据集行就是一条执行记录，报告可分组。
3. **数据配方是一等公民**：准备/清理与用例步骤同构（可录制/可编辑），可复用。
4. **唯一命名空间**：所有测试数据带 `run.id`，从第一天就做，避免以后并行/清理困难。
5. **先 API 建数据，UI 只做验证**：有 API 的场景优先用 HTTP 配方；没有 API 再用 UI 录制。
6. **GitHub Actions 只做 JUnit + artifacts**：不引入额外的 CI 平台耦合。

## 9. 开放问题

1. 被测系统是否提供测试数据准备/清理 API？没有的话，配方只能走 UI，速度和稳定性都会差。
2. 是否存在专用测试环境和 reset 接口？决定隔离策略是「唯一命名空间」还是「执行前重置」。
3. 表单/查询/CRUD 的首批页面清单是什么？用于先做 3 个模板验证。
4. 数据集由谁维护（测试同学/开发）？决定 CSV 还是表格编辑器优先。
5. GitHub Actions 能否访问被测环境（内网/白名单）？决定是否需要 self-hosted runner。
