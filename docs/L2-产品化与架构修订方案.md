# L2 产品化与架构修订方案（待确认）

> 本方案修订 v2 的两条边界，需确认后再开工：
> 1. **壳**：从「Electron + WebContentsView」改为「本地 Agent + 浏览器 UI + 真实 Chrome」，Electron 不再是必需项。
> 2. **协作**：本轮只做本地 Agent（CLI/二进制启动 + 本机 Chrome）；中央 Server 协作后置，架构预留。
>
> 版本：v3 · 2026-10-19 · 状态：待确认

---

## 0. 结论先行

- **Electron 不是必需品**。它现在提供的价值主要是「中栏嵌入浏览器」和「桌面安装包」，代价是被测浏览器被锁在 Electron 的 Chromium 里。
- **本地 Agent 就够了**：一个 CLI/二进制启动本机服务，浏览器打开 UI，Agent 控制真实 Chrome；不需要 Electron，也不需要先上中央 Server。
- **C/S 骨架已验证可行**：本地 Server + 两个客户端 + 本机 Chrome Agent 跑通录制、协作同步与回放；协作版以后可把 Server 拆出去，Agent 不变。
- **录制要有意图层**：执行层保留原语，意图层负责聚合、命名、分组、摘要；先做这一层，不改回放基础。
- **验收条件要产品化**：不是「自动推荐断言」，而是「录制时标记成功结果 → 生成验收卡 → 每次执行对比基线」。
- **测试数据不引入「变量」**：数据是录制自动产生的「本次数据」，用户直接改值、按需切「每次换一个」，不学模板语法。

## 1. 架构：本地 Agent + 浏览器 UI + 真实 Chrome

### 1.1 为什么改

| 维度 | Electron 内置 Chromium | 本地 Agent + 真实 Chrome |
| --- | --- | --- |
| 被测浏览器身份 | UA 含 Electron，版本跟随 Electron | 与用户日常浏览器一致 |
| Widevine / DRM | 不支持（无 CDM） | 支持 |
| 企业策略 / 客户端证书 / 扩展 | 受限 | 跟随本机 Chrome |
| 登录态 | 独立 session | 专用 profile，登录一次复用 |
| 无头 / CI | 需要 xvfb | 原生支持 |
| 访问方式 | 只能在本机 Electron 窗口里 | 任意浏览器打开 localhost；未来可局域网 |
| 更新 | 整包更新 | Agent 更新，Web UI 刷新即生效 |
| 协作基础 | 无 | HTTP/WS API 天然可共享 |

需要澄清：BrowserWing 这类工具并不是 CDP 能力比我们多，它占的便宜是**真实 Chrome 二进制 + 独立 profile + 浏览器窗口**。我们现在的嵌入模式已经是 Playwright 连 CDP，操作集是同一套。

### 1.2 目标形态

```
用户浏览器（Web UI）
    ↕ HTTP / WebSocket（默认 127.0.0.1，带 token）
atp-agent（CLI / 二进制，单进程）
    ├─ API / DB / 证据 / 运行队列
    ├─ 录制器注入、事件归一化、语义聚合
    ├─ Runner / Playwright
    └─ Chrome 生命周期
    ↕ CDP
真实 Chrome（专用 user-data-dir；可复用登录态）
```

- **启动方式**：`atp-agent` 启动本机服务，打印/打开本地 URL；首次生成访问 token。不做登录、不做多用户。
- **协作预留**：Agent 的 API/DB 边界按「以后可拆 Server」设计；协作版把 Server 抽出去，Agent 仍跑在每台机器上，本轮不实现。
- **录制**：Agent 用 Playwright 启动带专用 profile 的 Chrome，注入录制脚本；用户直接操作 Chrome 窗口，浏览器 UI 实时显示步骤。页面内注入一个轻量浮动工具条（录制状态、步骤数、「标记成功」、暂停/完成）。
- **回放**：Agent 启动 Chrome（或复用已开的受控窗口），浏览器 UI 显示步骤进度与逐步截图；需要「看着跑」时再开 CDP screencast，不作为 v1 必需。
- **证据**：截图/视频通过带 token 的 HTTP 提供，替代 `atp-evidence://`。
- **文件**：上传用页面 `input[type=file]` / Playwright `setInputFiles`；导出走 HTTP 下载。

### 1.3 取舍

**失去**

- 中栏嵌入式浏览器、单窗口体验；
- Electron 原生菜单/文件对话框/自定义协议；
- 一部分桌面集成（托盘、快捷键、自动更新）需要重新做。

**得到**

- 真实 Chrome 的身份、DRM、策略、扩展、登录态；
- 浏览器直接打开，跨平台、易更新；
- API 化之后，局域网共享和团队协作有天然基础；
- CI 可以直接跑 Agent + 无头 Chromium。

**缓解**

- 页面内浮动录制工具条补回「正在录制」的即时感；
- 回放用步骤截图 + 可选 screencast；
- 文件/下载/证据都走 Web 标准能力；
- 桌面启动器只负责「起服务 + 开浏览器」，不承载业务 UI。

### 1.4 迁移路径（不大爆炸）

1. **Spike（已完成初步验证）**：Server + 两个客户端 + 本机 Chrome Agent，跑通录制、协作同步与回放。
2. **Server/Agent 拆分**：Server 负责 API/DB/证据/协作；Agent 负责 Playwright/Chrome/录制器；单机模式同进程，协作模式独立部署。
3. **API 化**：把现有 IPC 契约映射为 REST + WebSocket；`window.atp.invoke` 换成 API client。
4. **客户端**：Renderer 改为浏览器可运行；证据 URL、文件选择、下载替换；需要原生能力再套 Tauri。
5. **启动器**：安装包/托盘启动 Server + Agent 并打开浏览器；Electron 仅作为可选壳或彻底移除。

`packages/model`、`packages/recorder`、`packages/runner` 已经零 Electron 依赖，可直接复用。DB repositories 也可复用，主要改的是传输层和壳。

### 1.5 Spike 目标（已完成初步验证，结果见 1.7）

- Agent 启动后，客户端能连接并新建项目/用例。
- 启动本机 Chrome（专用 profile），录制步骤，事件延迟 < 200ms。
- 从客户端触发回放，步骤结果在客户端可见。
- 全程不启动 Electron。
- screencast 能到 10–15fps（可选，不阻塞）。

初步验证通过；协作版还需补认证、权限、状态快照与运行队列。

### 1.6 C/S 与 B/S 的边界

先把两个轴分开，避免把「壳」和「协作」混在一起：

| | 本机 Agent | 中央 Server |
| --- | --- | --- |
| 桌面客户端 | C/S 单机 | C/S 协作 |
| 浏览器 UI | B/S 单机 | B/S 协作 |

- **C/S vs B/S 是 UI 壳**；**协作能力取决于有没有中央 Server**。
- 四个人用浏览器打开同一个服务，是 B/S 协作；桌面客户端连同一个服务，是 C/S 协作。两者可以共用同一套 API 和本机 Agent。
- 如果目标是协作：先做「中央 Server + 每台机器上的 Agent」，UI 先用浏览器（最快），需要原生能力时再套 Tauri 壳。不要因为壳的选择阻塞协作。
- 如果目标是嵌入浏览器：Tauri/系统 WebView 不是 Chrome，也嵌不了 Chrome；CEF 可以但重。现实方案仍是「外部真实 Chrome + screencast」。**C/S 壳本身不解决嵌入问题。**
- Tauri 2 可以作为 C/S 客户端：系统 WebView 承载 UI、Sidecar 启动 Agent、原生文件/托盘/更新；代价是 Rust 构建链与跨平台打包。建议在 Server/Agent 协议稳定后再做。

### 1.7 本地 Spike 结果（2026-10-19）

在 `/tmp` 做了最小验证，不进入产品代码：

- 本地 Server + 两个浏览器客户端 + 本机 Chrome Agent。
- Agent 通过 Playwright 控制真实 Chrome 155，注入现有 collector，事件经 `exposeBinding` 回传。
- 两个客户端看到完全一致的事件（3 条），回放结果一致，回放耗时 70ms。
- 传输延迟：单条 1–5ms（一次异常 1.2s，初步判断是首条 binding 回调/轮询抖动，需复测）。
- 专用 profile 持久化：localStorage 与 cookie 跨 Agent 重启保留。
- UA：真实 Chrome 155，不含 Electron；Electron 37 的 UA 含 `Electron/37.10.3`。
- Widevine：Electron `NotSupportedError`；真实 Chrome 在带 CDM 的 profile 下，指定 video/audio capabilities 时可用。Playwright 默认带 `--disable-component-update`，新建 profile 不会自动装 Widevine；需要正常启动 Chrome 或预置组件。
- 发现：后加入的客户端没有收到之前的 device 状态，Server 需要保存并补发状态快照。

结论：**本地 Agent + 真实 Chrome 可行；协作版可以沿用同一套 API，把 Server 拆出去。** 本轮只做本地 Agent，真正的协作成本（认证、权限、数据隔离、运行队列）后置。

### 1.8 边界

- **本轮只做本地 Agent**：默认只监听 `127.0.0.1`；不做登录、多用户、中央 Server。
- **中央 Server 协作**是独立里程碑：需要认证、权限、数据隔离、运行队列、浏览器 worker；Agent 的 API/DB 边界按可拆分设计，但本轮不实现。
- 开 LAN 必须显式开启并带 token。

### 1.9 Agent 的实现语言与分发

| 维度 | Node / TypeScript | Go | Rust |
| --- | --- | --- | --- |
| 复用现有 model/recorder/runner | ✅ 100% | ❌ 重写 | ❌ 重写 |
| Playwright 支持 | ✅ 官方 | playwright-go（社区） | playwright-rs（社区，pre-1.0） |
| 单二进制 | Node SEA 可行（Playwright 需外置） | ✅ 原生 | ✅ 原生 |
| 交叉编译 | 易 | 最好 | 好 |
| 开发速度 | 快 | 中 | 慢 |
| 更适合 | Agent 核心 | CLI/守护进程/Supervisor | Tauri 壳、纯 CDP |

**结论**

- **Agent 核心继续用 TypeScript/Node**：`packages/model`、`packages/recorder`、`packages/runner` 已经是 TS，Playwright 官方支持；换 Go/Rust 等于把定位/动作/断言引擎重写一遍，风险最大、收益最小。
- **单二进制可以做到**：Node SEA 打包 Agent；浏览器用本机 Chrome（`playwright-core` + `channel: chrome`），不要把浏览器打进二进制；Playwright 依赖 externalize，避免动态 require 被内联。
- **如果一定要原生单二进制**：Go 优于 Rust。Go 构建快、交叉编译简单、chromedp 成熟；`playwright-go` 是社区绑定但保留了 Playwright 语义。最稳的折中是 **Go 只做 supervisor/launcher，启动 Node runner**，不重写引擎。
- **Rust 留给以后可能的 Tauri 客户端壳**：Playwright Rust 绑定非官方，chromiumoxide 是 CDP 级；用它重写 Runner 成本高。
- BrowserWing 是 Go + React、直接走 CDP，所以它的单二进制路线成立；我们的差异是 Playwright 定位引擎，不能直接类比。

### 1.10 M0.5a 已落地（2026-10-19）

- 新增 `apps/agent`：`atp-agent` CLI 启动本地 HTTP/WS（token 保护），Playwright 启动真实 Chrome，复用 `@atp/recorder` / `@atp/runner`。
- 最小 Web UI：地址栏、开始/停止录制、实时步骤、保存用例、回放、逐步截图、内置演示页。
- 数据：`~/.atp-agent`（用例 JSON、Chrome profile、证据）；支持 `--headless`、`--no-open`。
- 冒烟验收：真实 Chrome 155 录制 4 步（输入/选择/勾选/点击保存）→ 保存 → 回放通过，4 张步骤截图；全程不启动 Electron。
- 已知限制：JSON 用例仓、最小 UI、无计划/套件/元素库页面；语义录制与自定义下拉在 M1；Chrome profile 被占用时需先关闭旧窗口。

## 2. 录制语义化 v1

### 2.1 目标

同一条「新建节目」录制：

- 之前：14 个平铺步骤，`点击 节目类型` + `点击 电影` 各算一步，用户看不出用例要做什么。
- 之后：≤10 个可读步骤，下拉合并为「选择 节目类型 = 电影」，弹窗有分组，用例有一句意图摘要；原始步骤仍可展开。

### 2.2 两层模型

**执行层（不变）**：click / fill / select / press / scroll / drag / wait / assert，保真、可回放、可导出。

**意图层（新增）**：

```ts
type CaseGroup = {
  id: string
  label: string              // "新建内容"
  kind: 'dialog' | 'section' | 'navigation'
}

type StepDisplay = {
  verb: string               // 填写 / 选择 / 开启 / 点击
  field?: string             // 内容名称 / 节目类型
  value?: string             // ${contentName} / 电影
}

// case 新增
intent?: string              // 一句话摘要
groups?: CaseGroup[]
// step 新增
groupId?: string
display?: StepDisplay
```

执行层只认原语；意图层是投影。**展示不改变执行**，避免为了好看牺牲稳定性。

### 2.3 聚合规则

只聚合高置信模式；不确定就保留原步骤并提示，不静默合并。

1. **自定义下拉 → 复合 select**
   - 第一次点击的目标具备 `role=combobox` / `aria-haspopup=listbox|menu` / 原生 `<select>`，或点击后出现了可见的 popup；
   - 1.5s 内第二次点击落在 `role=option|menuitem` 或 popup 内；
   - 合并为一个 `select`：元素 = 触发器，`params.value` = 选项文本。
   - Element Plus 的 `.el-select` / `.el-select-dropdown__item` 只作为**降级提示**，不作为定位基础。
   - 不确定时保留两次点击，并在草稿里标「可能是一个下拉选择，合并？」。
2. **开关/单选/复选 → 设置**
   - `input[type=checkbox|radio]`、`role=switch`、`aria-checked` 或关联 label 的点击；
   - 读取点击后的状态，显示「开启 显示标题」「选择 独播标识 = 非独播」。
3. **弹窗分组**
   - 点击后出现 `role=dialog` / `aria-modal`；到关闭/保存为止的步骤归入同一组；
   - 组名取弹窗标题；关闭后组结束。
4. **导航分组**
   - URL 变化、或点击菜单/标签导致主内容切换，归入「打开 xxx」。
5. **字段命名**
   - 优先级：`aria-label` → 关联 label → `placeholder` → `name` → 就近表单项标签（UI 库 class 仅作提示）→ 元素名。
   - 同一个名字出现多次时，用动作类型区分：「开启 显示标题」vs「填写 显示标题」。

### 2.4 Runner

- `select` 在原生 `<select>` 上走 `selectOption`。
- 自定义控件：点击触发器 → 等待可见 popup → 依次尝试 `role=option`、`role=menuitem`、popup 内文本 → 校验选中状态（`aria-selected` / 输入框值 / 触发器文本）。
- 失败时输出诊断：popup 是否出现、选项列表是什么、点击被谁遮挡。
- 导出 TS 时生成等价的复合 helper，不导出两次裸点击。

### 2.5 UI

- 步骤区默认「意图视图」，可切「原始步骤」。
- 语义卡片：`选择 节目类型 = 电影`，展开后看到两次点击、locator、命中候选。
- 分组头可折叠、可改名；每组支持「还原为原始步骤」。
- 录制结束后的草稿页显示置信度：「自动识别」/「待确认」；待确认项可一键合并或忽略。
- 用例头部显示意图摘要，可编辑。

### 2.6 测试

- Unit：语义聚合纯函数；ARIA listbox、Element Plus 风格 DOM、单选组、弹窗分组、歧义不合并。
- Integration：Playwright fixture 录制 → 语义草稿 → 回放通过。
- E2E：fixture 上录制，UI 显示语义步骤；计划执行回放通过。
- 回归：现有 click/fill/iframe 用例不受影响。

### 2.7 非目标（v1）

- 日期选择器、多选、树选择、纯键盘选择；
- 多标签/多窗口；
- LLM 生成意图摘要（先用模板）；
- 验收条件（下一节单独设计）。

### 2.8 验收

- 截图中的流程录制后，下拉各合并为一步，显示字段名与值。
- 弹窗步骤成组，用例有一句可读摘要。
- 语义用例回放通过；复合 select 能重新打开并正确选中。
- 歧义场景不被静默合并，能一键还原。

## 3. 验收条件产品化（修订）

「自动推荐断言」不够产品化：它仍然是技术语言、事后猜测，用户没有「这次算成功」的主动表达。改为：

### 3.1 录制时标记成功

- 页面内浮动工具条提供「✓ 标记成功」，快捷键同效。
- 点击时捕获**结果快照**：URL、可见提示（toast/alert）、弹窗状态、主内容区关键行、截图、文本摘要。
- 这是用户的主动动作，语义明确：**“我看到的就是成功的样子”**。

### 3.2 验收卡

录制结束后展示自然语言条件，而不是断言类型：

```
验收条件
  ✓ 出现提示「保存成功」            [编辑]
  ✓ 列表中出现「${contentName}」     [编辑]
  ✓ 新建弹窗已关闭                  [编辑]
  + 添加条件
```

- 条件从快照生成，用户可删改；「添加条件」给的是业务结果选项（提示/列表/字段值/状态/地址/数量），不是 `visible/text/value`。
- 高级模式才展开底层断言。
- 条件可引用变量，保证每次执行校验的是本次创建的数据。

### 3.3 基线对比

- 每次执行结束与快照对比，报告显示「预期 vs 实际」：
  - 列表没有出现 `节目_20261019_1030`；当前列表 20 行，最新一行是 `节目_20261018_...`。
- 失败附截图与差异字段。
- 产品有意变更时，一键「更新验收基线」，展示 diff 后确认。
- 场景模板（新建/编辑/删除/查询）预置验收条件与清理动作，用户选模板而不是选断言。

### 3.4 实现时机

- 语义录制 v1 先把「结果信号」采集好（toast、弹窗关闭、列表变化、URL），为验收卡做数据准备。
- 验收卡与基线作为下一个切片，不混在 v1 里。

## 4. 测试数据：不要引入「变量」这个概念

上一版还是开发者思维：值单元格、`{}` 菜单、提取为变量、生成器、预检。用户第一次看到仍然要理解一套机制。优秀的产品设计应该让用户**看到的就是他刚录的东西**，不需要先学「变量」。

### 4.1 核心原则

- **数据从录制里自动长出来**：每次 fill/select/toggle 都自动成为「本次数据」的一行，用户不需要创建变量。
- **不出现新名词**：界面只说「本次数据」「每次换一个」「多组数据」「共用数据」，不出现变量/作用域/生成器/数据集。
- **直接改值**：点步骤里的值或在数据面板里改，两处同步。
- **默认固定，按需变化**：默认使用录制时的值；名称/标题/编号这类字段提供「每次换一个」的开关，避免重复。
- **运行前不弹窗**：数据面板本身就是预览；缺数据就地提示。

### 4.2 界面

录制结束后：

```
本次数据
内容名称   ddefe     [每次换一个 ▾]  下次：节目_20261019_1031
显示标题   fewfe     [固定 ▾]
节目类型   电影       [固定 ▾]
...
[用多组数据跑]   [在多个用例间共用]
```

- 点「每次换一个」展开的是中文选项：每次换一个名字 / 递增编号 / 随机手机号 / 当前日期 / 从列表里选 / 固定值，不用填表单。
- 点「用多组数据跑」变成表格：一行一组；可粘贴 Excel/CSV；报告显示「第 2 组」。
- 点「在多个用例间共用」才把这条数据提升为项目级共用数据；默认不暴露作用域。
- 密码自动标记为密钥，显示掩码。
- 高级模式才显示变量名和 `${}`，普通用户永远不需要看到。

### 4.3 和验收条件的联动

验收条件直接用数据行的名字：`列表中出现「内容名称」这一行的值`，不写 `${contentName}`。用户看到的是业务语义。
