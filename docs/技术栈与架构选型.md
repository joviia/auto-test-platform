# ATP 技术栈与架构选型

> 状态：待确认（2026-10-19）
> 适用形态：本地 Agent（CLI + 本地 HTTP/SSE + 真实 Chrome）+ 浏览器 UI
> 原则：本地单机优先、不做服务端/云；正确性优先于兼容性；不保留 Electron 旧形态。

## 2. 运行时与语言

### 2.1 Node.js

- **目标版本：Node 24 LTS**
- **最低版本：22.17**
  - MikroORM 7 的 `engines` 为 `>=22.17.0`
  - Node 24 已是 LTS，生命周期更长
- `package.json` 写入：

```json
{
  "engines": { "node": ">=22.17" }
}
```

- 不在运行时依赖 `node:sqlite`。SQLite 使用 better-sqlite3，避免 experimental API 的版本波动。

### 2.2 ESM

所有包统一：

```json
{ "type": "module" }
```

TypeScript 配置：

```json
{
  "module": "NodeNext",
  "moduleResolution": "NodeNext",
  "verbatimModuleSyntax": true,
  "types": ["node"]
}
```

约定：

- 相对导入必须带 `.js` 扩展名
- `__dirname` 改为 `import.meta.dirname`
- 禁止 `enum`、`namespace`、参数属性（便于类型剥离与工具链兼容）
- CLI 使用顶层 `await`，但 `main().catch()` 仍保留统一错误出口

### 2.3 TypeScript

- 直接采用 TypeScript 7.0（Go 原生编译器）
- 必须显式设置 `types`、`rootDir`、`moduleResolution`
- `moduleResolution: node/node10/classic` 在 TS 7 中是硬错误
- 不使用装饰器；MikroORM 用 `defineEntity`，因此不依赖 `emitDecoratorMetadata`
- 不使用 `tsup --dts`：
  - TS 7.0 暂不提供程序化编译器 API
  - 内部包不需要发布 `.d.ts`
  - 如未来需要声明文件，使用 `tsc --emitDeclarationOnly` 或把声明生成拆成独立任务
- 工具链以 TS 7 为前提选型；不保留 TS 6 回退分支
  - 如果某个工具阻塞，替换该工具或调整构建方式，而不是降级 TypeScript

### 2.4 为什么不用 Bun 运行时

结论：**不采用 Bun 作为 Agent/runner 运行时**，只保留 Node。

原因不是“保守”，而是硬依赖冲突：

- 整个执行引擎基于 Playwright
- Playwright 官方没有宣布支持 Bun；维护者在 issue #38095 中明确表示“不在 Bun 上测试，不推荐”
- 社区实测在 Bun 下 `chromium.launch` 与 `connectOverCDP` 会超时，而 Node 下正常
- Bun 1.4 博客声称 Playwright 可运行，但官方支持与 Windows 路径仍有问题
- 我们还要用 better-sqlite3（N-API 原生模块）和 MikroORM，进一步增加不确定性

因此：

- **Node 负责运行时与浏览器驱动**
- 如果未来 Playwright 官方支持 Bun，再评估迁移
- 不使用 `bun build --compile` 做单文件分发；原因见 §12 与 §17.6


### 4.3 启动与退出

启动流程：

1. 读取 `settings.json`，CLI 参数覆盖
2. `doctor` 轻量检查：Node 版本、数据目录可写、端口可用
3. 获取单实例锁；已锁则读取 `agent.json`，打开已有 UI
4. 初始化 MikroORM，执行 `migrator.up()`
5. 启动 Hono server（仅绑定 `127.0.0.1`）
6. 启动 Chrome（优先 `channel: 'chrome'`，失败回退 Playwright Chromium）
7. 打印带 token 的 UI 地址，按需打开浏览器

退出：

- `signal-exit` 统一处理 SIGINT/SIGTERM/异常
- 关闭 Chrome、关闭 server、释放锁
- 保留证据与日志，不做清理

### 4.4 单实例

- `proper-lockfile` 锁 `<data-dir>/.agent.lock`
- 锁内写 `agent.json`：`{ pid, port, token, startedAt, version }`
- 第二个实例：
  - 检测到锁 → 读取 `agent.json`
  - 打开已有 UI（`--no-open` 时只打印地址）
  - 不启动第二个 Chrome（Chrome profile 不能共享）

### 4.5 doctor

检查项：

- Node 版本是否满足 `>=22.17`
- 数据目录、日志目录、证据目录可写
- SQLite 文件与迁移状态
- Chrome/Chromium 是否可用；Playwright 浏览器是否安装
- 端口占用
- 单实例锁状态
- 更新检查结果

输出：`[✓]/[!]/[×]` + 建议动作 + 日志路径。

### 4.6 终端 UX 原则

- 终端是“启动器 + 诊断器”，不是主 UI
- 成功启动只打印：版本、UI 地址、数据目录、Chrome 引擎
- 失败时打印：原因 → 建议动作 → 日志路径
- `--json` 时不输出颜色/spinner/更新提示，保证可管道处理
- 步骤、证据、报告全部在 Web UI

### 5.3 SSE

事件：

- `recording-status`
- `recording-step`
- `replay-progress`
- `plan-progress`
- `ai-stream`（后续）
- `ai-tool`（后续）

使用 Hono `streamSSE`：

- 每 15s 心跳
- 客户端断开时清理订阅
- token 支持 header 或 query
- `Cache-Control: no-cache, no-transform`

### 5.4 window.atp 垫片

服务端注入最小脚本：

```js
window.atp = {
  mode: 'web',
  token,
  invoke: (channel, payload) => fetch('/api/invoke', ...),
  on: (name, fn) => EventSource 订阅,
}
```

- `on('event:recording-step')` 自动映射到 SSE 的 `recording-step`
- 最后一条事件缓存，监听器注册时补发
- 与 Electron preload 的契约保持一致，renderer 无感迁移

### 5.5 安全

- 仅监听 `127.0.0.1`
- 所有 API 校验 `x-atp-token` 或 `?token=`
- 状态变更接口额外校验：
  - `Content-Type: application/json`
  - `Origin`/`Host` 只允许 `http://127.0.0.1:<port>` / `http://localhost:<port>`
- 证据文件路径做白名单与路径穿越校验
- 不启用 CORS

## 6. 数据层

### 6.1 依赖

| 库 | 版本 |
| --- | --- |
| @mikro-orm/core | 7.2.5 |
| @mikro-orm/sqlite | 7.2.5 |
| @mikro-orm/migrations | 7.2.5 |
| better-sqlite3 | 13.0.3（由 sqlite driver 使用） |

### 6.2 实体定义

使用 `defineEntity`，不使用装饰器：

```ts
import { defineEntity, p, type InferEntity } from '@mikro-orm/core'

export const Case = defineEntity({
  name: 'Case',
  tableName: 'cases',
  properties: {
    id: p.string().primary(),
    projectId: p.string().index(),
    moduleId: p.string().nullable(),
    name: p.string(),
    startUrl: p.string(),
    variables: p.json().nullable(),
    intent: p.string().nullable(),
    groups: p.json().nullable(),
    createdAt: p.string(),
    updatedAt: p.string(),
    steps: () => p.oneToMany(CaseStep).mappedBy('case'),
  },
})

export type Case = InferEntity<typeof Case>
```

实体清单：

- `Project`
- `Module`（自关联 parent/children）
- `Case`
- `CaseStep`
- `Element`
- `Suite`
- `SuiteItem`
- `Plan`
- `PlanItem`
- `PlanRun`
- `Run`
- `RunStep`
- 可选：`AiSession` / `AiMessage`

### 6.3 Repository 与 Unit of Work

- 每个聚合一个 `EntityRepository`
- 对外保留现有 DTO 形态（`CaseRow`、`RunRow`…），UI 不需要感知 ORM
- 写操作：

```ts
await em.transactional(async (em) => {
  const c = em.create(Case, { ... })
  c.steps.add(em.create(CaseStep, { ... }))
  await em.flush()
})
```

- 读操作：

```ts
const cases = await em.find(
  Case,
  { projectId },
  { populate: ['steps'], orderBy: { updatedAt: 'DESC' } },
)
```

- 每个 HTTP 请求/操作使用 `em.fork()`，避免长生命周期 Identity Map 污染

### 6.4 迁移

- 使用 `Migrator` + 显式 `migrationsList`：

```ts
const orm = await MikroORM.init({
  entities: [Project, Module, Case, CaseStep, Element, Suite, SuiteItem, Plan, PlanItem, PlanRun, Run, RunStep],
  extensions: [Migrator],
  migrations: {
    migrationsList: [Migration20261019Initial],
  },
  dbName: join(dataDir, 'atp.db'),
})
await orm.getMigrator().up()
```

- 不使用文件扫描/glob，确保 tsup 打包后仍可运行
- 新迁移追加到 `migrationsList`
- 启动时自动 `up()`；失败则打印原因并退出

### 6.5 数据目录

```
<data-dir>/
  atp.db
  atp.db-wal
  atp.db-shm
  profile/                 # Chrome 持久化 profile
  runs/<runId>/            # 截图/视频/证据
  logs/                    # JSONL 日志
    agent-YYYY-MM-DD.jsonl

```

### 6.6 旧库处理

- 预发布阶段不做旧数据兼容
- 启动时检测旧版 `__drizzle_migrations`：
  - 将 `atp.db` 重命名为 `atp.legacy-<时间>.db`
  - 重建新库
  - 打印明确提示与备份路径
- 不做自动数据搬运

### 6.7 SQLite 配置

- `journal_mode = WAL`
- `busy_timeout = 5000`
- 外键开启
- 单进程单实例（锁保证）

### 10.2 设计原则

- AI 是 Agent 内部的一层能力，不是独立服务
- 所有 AI 工具与 MCP 工具共用 **Tool Registry**
- 工具分为只读/写两类，仅用于审计标注；v1 不做权限拦截
- 所有工具调用写入审计日志（参数、结果、耗时、调用方）
- API Key 不进入浏览器；只存在 Agent 进程
- 不引入 LangChain/LangGraph；抽象过重，和我们的工具模型不匹配

### 10.3 Tool Registry

```ts
export interface AtpTool {
  name: string
  description: string
  input: z.ZodType
  readOnly: boolean
  handler: (input: unknown, ctx: ToolContext) => Promise<unknown>
}
```

首批工具：

- 读：
  - `list_projects`
  - `list_cases`
  - `get_case`
  - `list_runs`
  - `get_run`
  - `get_step_evidence`
  - `get_current_page`
  - `get_recording_status`
- 写：
  - `navigate`
  - `start_recording`
  - `stop_recording`
  - `save_case`
  - `run_case`
  - `run_plan`
  - `stop_run`
  - `update_case`
  - `update_element`

适配器：

- MCP Server：`@modelcontextprotocol/server` v2
- AI SDK：`tool({ description, inputSchema, execute })`
- 未来可加 CLI/HTTP，共享同一注册表

### 10.4 AI 使用场景（分阶段）

1. **报告 Copilot**
   - 解释失败原因、定位器失效、证据摘要
2. **用例编辑助手**
   - 根据自然语言生成/修改步骤，直接写入并记录变更审计
3. **语义意图生成**
   - 用 AI 改进录制后的 `intent` 与 `display`，替代纯模板
4. **自愈建议**
   - 分析失败截图/DOM，建议并写入新的 locator，保留变更记录
5. **测试计划生成**
   - 从需求/URL 生成候选用例与计划

### 10.5 运行时与持久化

- `ToolLoopAgent` + `stopWhen: isStepCount(n)`
- 流式输出通过 Agent 的 SSE 转发到 Web
- 会话与工具调用写入 SQLite（`AiSession` / `AiMessage`）或 JSONL
- 预算控制：
  - 最大步数
  - 最大 token / 成本
  - 超时
- 失败可重试；工具错误作为结构化结果返回给模型

### 10.6 安全

- v1 不做写工具确认；所有工具调用写审计日志
- MCP stdio 直接继承本地用户权限；HTTP MCP 仍校验 token/Origin
- 页面内容/证据可能含敏感数据；发送给模型前限制大小并记录用途
- API Key：
  - 优先环境变量 `ANTHROPIC_API_KEY`
  - 可选 OS keychain（`@napi-rs/keyring`）
  - 不在 `settings.json` 明文保存
- 审计日志不记录 token/API Key；工具参数中的密码类字段做脱敏

## 12. 打包、分发与自动更新

### 12.1 npm 单包

- 包名：`@atp/agent`
- `bin`: `atp-agent` → `dist/cli.js`
- `files`: `dist`, `README.md`, `LICENSE`
- `engines`: `>=22.17`
- 内部包通过 tsup 内联，用户只需安装一个包
- external：
  - `playwright`
  - `better-sqlite3`
- 安装后提示：
  - 优先使用系统 Chrome
  - 没有 Chrome 时运行 `atp-agent install-browser`

### 12.2 自动更新：两种模式，均落地

统一由 `UpdateService` 负责，根据安装形态选择模式：

| 安装形态 | 模式 | 行为 |
| --- | --- | --- |
| npm 全局安装 | npm 模式 | 检查更新 + `atp-agent update` 执行全局安装 |
| 版本化独立包 | bundle 模式 | 后台检查 + 下载 + 校验 + 原子切换，真正静默更新 |

#### 12.2.1 更新源与清单

- 默认更新源：GitHub Releases；可通过 `ATP_UPDATE_URL` 或 `settings.json` 覆盖
- 清单 `latest.json`：

```json
{
  "version": "0.2.0",
  "channel": "stable",
  "publishedAt": "2026-10-19T00:00:00Z",
  "minVersion": "0.1.0",
  "platforms": {
    "darwin-arm64": { "url": "https://...", "sha256": "...", "size": 0 },
    "darwin-x64": { "url": "https://...", "sha256": "...", "size": 0 },
    "linux-x64": { "url": "https://...", "sha256": "...", "size": 0 },
    "win32-x64": { "url": "https://...", "sha256": "...", "size": 0 }
  }
}
```

- 签名：
  - manifest 使用 Ed25519 签名
  - 公钥内置于启动器
  - tarball 校验 SHA-256
- 频道：`stable` / `beta`，通过 `--channel` 选择
- 检查频率：默认 24h，带随机抖动；缓存到 `<data-dir>/update-check.json`

#### 12.2.2 npm 模式

- `atp-agent update`
  - 检测安装方式（npm/pnpm/yarn/bun）
  - 执行对应的全局安装命令
  - 校验新版本并提示重启
  - 权限不足时打印精确命令
- 后台检查
  - 最多每 24h 请求一次 npm registry
  - 在命令结束时向 stderr 提示：
    `新版本 0.x.y 可用：atp-agent update`
  - 关闭方式：
    - `--no-update-check`
    - `ATP_NO_UPDATE_CHECK=1`
    - CI 环境自动关闭
    - `--json` 自动关闭
- 不在后台静默执行全局安装
  - 修改全局包不安全，且不同包管理器行为不一致
  - npm 模式只做“检查 + 显式更新”

#### 12.2.3 bundle 模式（真正静默更新）

目录：

```
~/.atp-agent/
  bin/atp-agent            # 启动器
  current -> versions/0.2.0
  versions/0.1.0/
  versions/0.2.0/
  browsers/                # 可选，install-browser 下载的 Chromium
```

bundle 内容：

- `runtime/node`：对应平台的 Node 运行时
- `app/dist`：tsup 产物 + Web 资源
- `app/node_modules`：生产依赖（playwright、better-sqlite3、tar 等）
- `bin/atp-agent`：启动器

更新流程：

1. 启动器解析 `current`
2. `UpdateService.check()` 在后台执行，不阻塞启动
3. 发现新版本：
   - 下载到 `versions/.staging-<version>`
   - 校验 manifest 签名与 tarball SHA-256
   - 解压
   - 健康检查：`node app/dist/cli.js version --json`
4. 健康检查通过后：
   - 原子重命名为 `versions/<version>`
   - 原子切换 `current`
   - 保留上一版本用于回滚
5. 应用时机：
   - 默认下次启动生效
   - 如果当前空闲（未录制、未回放、未执行计划），可提示立即重启
   - 录制/回放/计划执行期间只下载与暂存，不切换
6. 失败处理：
   - 校验失败、下载中断、健康检查失败 → 保留旧版本
   - 记录日志并清理 staging

平台差异：

- macOS / Linux：`current` 为符号链接
- Windows：使用 junction；不可用时退回 `current.txt` 指针，由启动器解析

Playwright：

- 默认使用系统 Chrome
- 可选 `install-browser` 下载 Chromium 到 `~/.atp-agent/browsers`

#### 12.2.4 发布流水线

`scripts/build-release.mjs`：

1. 构建 packages / agent / web
2. 生成生产依赖目录（`pnpm deploy --prod` 或等价方式）
3. 复制当前平台 Node 运行时
4. 生成 `atp-agent-<version>-<os>-<arch>.tar.gz`
5. 计算 SHA-256
6. 生成并签名 `latest.json`
7. 上传到 GitHub Releases

CI matrix：macOS arm64 / macOS x64 / Linux x64 / Windows x64。

#### 12.2.5 更新测试

- 单元：semver 比较、manifest 验签、SHA-256、staging 原子切换
- E2E：本地 HTTP 更新服务器提供 v1/v2 bundle
  - 启动 v1
  - 触发检查与下载
  - 断言 `current` 指向 v2
  - 断言 v2 可启动
- 失败用例：
  - 校验和不匹配
  - 签名无效
  - 下载中断
  - 健康检查失败
  - 以上情况都必须保留旧版本

### 12.3 为什么不用 Bun standalone

- Playwright 官方不支持 Bun（§2.4）
- `bun build --compile` 与 Playwright 存在已知不兼容
- better-sqlite3/MikroORM 增加不确定性
- 版本化 Node 包即可实现静默更新，不需要换运行时

## 17. 被否决的选项

### 17.1 Electron

- 约束 Chromium 版本与能力
- 需要维护 main/preload/renderer 三套边界
- 无法像真实 Chrome 一样使用用户环境
- 结论：删除

### 17.2 node:sqlite

- experimental API，已遇到 `setReturnArrays` 版本差异
- Node 版本耦合
- 结论：换 better-sqlite3

### 17.3 Drizzle ORM

- 类型安全 SQL 构造器，不是 JPA/MyBatis-Plus 式 Repository 体验
- 结论：换 MikroORM

### 17.4 TypeORM

- 装饰器依赖 `emitDecoratorMetadata`
- esbuild/tsup 不生成装饰器元数据，需要插件或 EntitySchema 妥协
- 1.0 虽已发布，但上述构建问题会引入“补丁”
- 结论：不采用

### 17.5 Prisma

- 查询体验好，但运行时迁移只能走 CLI
- 本地嵌入式 CLI 每次启动 shell out 不干净
- 结论：不采用

### 17.6 Bun

- Playwright 官方不支持；实测 launch/CDP 超时
- 结论：不作为运行时；不作为构建器；包管理器可选但不支持

### 17.7 LangChain / LangGraph

- 抽象层过重，工具/流程模型与我们的 Tool Registry 不匹配
- 结论：不采用

### 17.8 ESLint + Prettier

- Biome 2 已覆盖 lint/format，配置更简单
- 结论：使用 Biome

### 17.9 Next.js / SSR

- 本地 SPA 不需要 SSR
- Vite + React 足够
- 结论：不采用

## 18. 风险与待确认

1. **TypeScript 7 工具链**
   - TS 7 无程序化编译器 API（7.1 才有）
   - tsup dts、部分类型工具可能不兼容
   - 方案：不使用 dts；遇到阻塞时替换工具或调整构建，不降级 TypeScript
2. **静默自动更新**
   - bundle 模式需要发布流水线、签名、平台矩阵
   - 必须在录制/回放/计划执行期间只暂存、不切换
   - 失败必须保留旧版本
3. **Node 22.17 门槛**
   - MikroORM 7 要求 `>=22.17`
   - 用户需升级 Node；README 与 `engines` 必须明确
4. **Windows**
   - Playwright 在 Windows 的 Chromium 启动/路径存在差异
   - 首个版本以 macOS 为主，Windows 作为验证项
5. **AI/MCP 写操作**
   - v1 不做权限拦截，所有写操作依赖审计日志与数据备份
   - 需要保证工具参数与结果可追溯
6. **AI Key 存储**
   - 环境变量 vs OS keychain；首个版本建议环境变量
7. **MikroORM 学习曲线**
   - Unit of Work/Identity Map 与现有手写仓储差异较大
   - 需要一次团队内的用法约定
8. **AI 成本与隐私**
   - 页面内容/证据发送给模型的范围与脱敏策略需明确
