> S1 交付的是一条不依赖 AI 的确定性链路：读取当前页面的字段约束 → 生成测试设计矩阵 → 用户勾选/修改数据 → 生成带断言的用例 → 在真实 Chrome 中逐条执行 → 按需保存到用例库。即使没有配置模型或密钥，整条链路也可用。

## 1. 交付范围

| 层 | 交付物 |
|---|---|
| 领域模型 | `DesignField` / `DesignScenario` / `DesignMatrix` / `DesignCase` / `DesignResult`；新增 `expectedValue` |
| 规则引擎 | 新包 `@atp/test-design`：必填、长度、格式、正常流四类规则，输出场景、跳过原因与统计 |
| 字段识别 | `ChromeController.designPage()`：可见输入框、下拉、文本域，提取标签、`required`、`minlength/maxlength`、`min/max`、`type`、选项与提交按钮 |
| 语义断言 | Runner 新增 `fieldInvalid`、`fieldError`，兼容原生约束、Element Plus、Ant Design 与项目自定义标记 |
| Agent | `design:analyze` / `design:generate` / `design:run` / `design:stop` + `event:design-result` |
| UI | AI 对话内触发（说「为当前页面生成测试设计」或点空状态建议）、矩阵卡（勾选、改数据、跳过原因、逐条结果）、生成/执行/停止/保存 |
| 用例库 | 「保存到用例库」把生成结果写入当前项目；AI 不静默写入，必须由用户点击 |

## 1.1 对话内触发

测试设计不是打开页面后的一个独立工具按钮，而是 AI 对话能力的一部分：

- 在 AI 输入框说「为当前页面生成测试设计」「检查必填/长度/格式边界」即可触发；空状态也提供一键建议。
- 命中意图时不调用模型，直接走确定性规则引擎，因此无密钥、演示模式下同样可用。
- 结果以两条 AI 消息（开始分析、结果摘要）+ 矩阵卡出现在对话区，后续生成/执行/保存仍在卡片内完成。
- 没有打开页面时，AI 回复「没有读到可分析的页面」，不产生空分析。
- **列表/查询页自动打开新建表单**：识别到「查询/搜索」按钮且有「新建/新增/创建」入口时，会点击入口、等待弹窗或新页面出现，再分析表单；只打开空表单，不填写、不保存。矩阵卡会注明「已打开…表单进行分析」。
- 弹窗表单只分析当前浮层，不会把背景列表字段混进来；生成的用例会先点击「新建」入口再填写，保证每条用例可独立回放。
- 当前页面是表单浮层时直接分析浮层，不重复打开入口。
- 没有「新建/新增」入口的查询页仍明确回复 S1 只支持表单页，不生成必然失败的表单场景。

## 2. 规则行为

### 必填

- 必填文本/数字/日期字段：生成一条空值场景，预期字段无效 + 有错误提示。
- 必填来源：原生 `required` / `aria-required`，以及 Element Plus `.is-required`、Ant Design 等组件容器的必填标记。
- 必填下拉（原生或自定义）：没有默认值时生成「空值」场景，不自动选择任何选项；有默认值时跳过，因为无法在不改变业务状态的情况下构造空值。
- 纯空格不默认视为空：是否 trim 属于产品规则，S1 不生成必然猜测的用例，留到 S2 探测。

### 长度

- `minlength`：生成 `min-1`（无效）与 `min`（通过）。
- `maxlength`：生成 `max`（通过）与 `max+1`（截断）。
- `max+1` 的预期是**浏览器截断**，不是报错：原生 `maxlength` 会阻止继续输入，用例断言输入值被截为 `max` 且提交成功。
- 没有长度约束的字段明确跳过，不生成假场景。

### 格式

- `email`：非法邮箱。
- `tel`：位数不足。
- `url`：非法地址。
- `number`：有 `max` 取 `max+1`，有正数 `min` 取 `min-1`；两者都没有则跳过并说明原因。
- 每条负向场景同时断言 `fieldInvalid`、`fieldError`，并保持页面 URL 不变。

### 正常流

- 单步表单：用唯一合成数据填满所有可填字段，提交后断言页面成功文案（默认「保存成功」）。
- 弹窗表单：每条用例先点击列表页的「新建」入口，再填写与提交。
- 多步表单（提交按钮是「下一步 / 继续」）：S1 只生成第一步的负向校验，正向流程跳过并说明原因。
- 存在无法自动填写的必填字段（自定义下拉）时，正常流跳过，避免生成必然失败的用例。
- 演示页的成功文案是「保存成功：{名称}」，按包含匹配。

## 3. 执行与结果

- 场景按勾选顺序逐条执行，每条生成独立 `runId`，证据截图写入 `runs/<runId>`。
- 每条用例回放前都重新加载 `startUrl`（同 URL 也强制 reload），确保上一次留下的弹窗、表单状态不会影响下一条用例。
- 结果只回显在矩阵卡（通过 / 未通过 / 已停止），**S1 不写入运行记录、不进报告页**；失败详情在「未通过」标记的 `title` 中。
- 停止会中断当前回放，剩余场景标记为已停止。
- 执行结果不改变用例库；只有用户点击「保存到用例库」才写入。

## 4. 关键决策

1. **规则确定性优先**：S1 不调用 AI。字段识别失败时宁可跳过并给出原因，也不生成不可信场景。
2. **截断而非报错**：`maxlength` 是输入阶段的浏览器约束，把它当成后端校验失败会产生必然失败的用例。S1 用 `value` 断言验证截断结果；后端长度校验留到接口/服务端测试层。
3. **语义断言兜底文本**：优先 `aria-invalid`、原生 `checkValidity()`、常见表单组件的错误类；错误提示读取原生 `validationMessage` 或 `role=alert` / Element Plus / Ant Design 节点。Element Plus 只渲染 `.el-form-item__error`、不写 `is-error` 时也判定为无效。
4. **不自动保存**：生成结果是草稿；保存动作与 AI 计划卡一样，由用户确认。
5. **执行不落库**：避免把探索性执行混入正式运行历史；正式回归仍走已保存用例与计划。
6. **允许 AI 打开空表单**：列表页没有可测表单时，自动点击「新建」入口并分析弹窗；只打开、不填写、不保存，属于可逆操作。
7. **只断言能确定的结果**：纯空格、已有默认值的下拉、多步表单的正向流程都明确跳过，不用猜测制造失败。

## 6. 已知限制

- 只识别 HTML 约束与常见组件类名；自定义组件通过 `aria-invalid` / 错误文案等运行时信号断言，但不读取其内部校验规则。
- 必填推断依赖 `.is-required`、星号等标记，可能存在误判；不确定的场景会在执行结果中暴露。
- 查询/列表页有「新建」入口时会自动打开表单；没有入口且不是可识别表单时明确跳过。列表、查询、分页规则属于 S3。
- 自定义下拉：必填留空可测；但不会自动选择选项，正向场景会跳过。
- 纯空格是否等于空取决于产品规则，S1 不生成；留给 S2 的错误文案/规则探测。
- 多步表单只测第一步的负向校验，正向流程需要后续步骤建模。
- 表格行内编辑、分页器等控件不纳入表单设计。
- 重复校验、错误文案自动发现、项目级规则配置未实现。
- 未做运行记录/报告页集成、覆盖统计与数据集。
- 自动打开新建表单属于页面操作，可能触发埋点或草稿；不会填写、保存或提交数据。
- 正常流会真实提交表单；演示页安全，真实业务页需用户自行确认测试数据。
- 场景数据编辑后旧草稿会清空，需要重新生成。
